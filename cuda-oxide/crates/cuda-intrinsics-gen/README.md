# cuda-intrinsics-gen

Extractor and deterministic source generator for cuda-oxide's intrinsics.

It reads `intrinsics/catalog.json` and the libdevice math shard, and writes every
generated file in the intrinsic pipeline. `MANAGED_GENERATED_ROOTS` in
`src/generate.rs` lists the
ten directories it owns, where `generate` writes outputs and removes stale
marker-bearing files:

- `cuda-oxide/crates/cuda-intrinsics/src/generated/`: the raw intrinsic declarations;
- `cuda-oxide/crates/cuda-device/src/generated/`: the safe device wrapper modules;
- `cuda-oxide/crates/dialect-nvvm/src/ops/generated/`: the `dialect-nvvm` ops;
- `cuda-oxide/crates/mir-importer/src/translator/terminator/intrinsics/`: the importer
  dispatch arms that recognize each intrinsic by name (the enclosing
  `cuda-oxide/crates/mir-importer/src` is listed as a root of its own);
- one generated file each in `cuda-oxide/crates/cuda-oxide-codegen/src` (target
  requirements), `cuda-oxide/crates/mir-lower/src/convert` (conversion interfaces), and
  `cuda-oxide/crates/rustc-codegen-cuda/src` (collector predicates);
- `intrinsics/probes/`: the per-intrinsic PTX probe evidence;
- `crates/dialect-mir/src/generated/`: shared compiler math dispatch.

Generated files carry a
`// @generated by cuda-intrinsics-gen ... DO NOT EDIT.` banner; edit the
catalog or shard and regenerate instead.

```
cuda-intrinsics-gen extract --intrinsics-json FILE --nvptx-json FILE
cuda-intrinsics-gen extract --llvm-src DIR --llvm-tblgen FILE
cuda-intrinsics-gen generate
cuda-intrinsics-gen check
cuda-intrinsics-gen extract-libdevice --libdevice FILE --llvm-dis FILE
cuda-intrinsics-gen verify-libdevice --libdevice FILE --llvm-dis FILE
cuda-intrinsics-gen coverage [--family NAME]
cuda-intrinsics-gen check-abi-history --base-ref REF
cuda-intrinsics-gen probe [--all | --intrinsic ID] [--llc FILE] [--skip-terminal] [--per-target]
cuda-intrinsics-gen probe --candidate --intrinsic ID --llc FILE --gpu-target TARGET --ptx-feature FEATURE (--ptxas FILE | --skip-terminal)
```

Three of these gate CI (`unit-tests.yml`): `check` proves the committed
generated sources match what the generator produces, `probe --all --per-target`
checks the pinned `llc` identity and exact emitted PTX for every target declared
by each route, and
`check-abi-history` keeps the intrinsic ABI ledger append-only.

Generation shells out to `rustfmt`, which the pinned toolchain provides.

## Libdevice math family

`intrinsics/overlay/libdevice_math.toml` is the schema-2 source of compiler math
dispatch. It covers 120 of 124 libm exports (`f32`/`f64`), including tgamma,
ilogb, ldexp/scalbn, frexp, modf, remquo, lgamma_r, C23 `fmaximum*`/`fminimum*`,
j1, and the 22 plain libm aliases, plus the core-only powi and fmuladd
intrinsics.

The renderer writes two outputs:

- `crates/dialect-mir/src/generated/libdevice_math.rs`: the shared math enum,
  lowering dispatch (`RustFloatMathLowering`), placeholder constants,
  compiler-path and alias dispatch, operand counts, libdevice/native LLVM
  symbols, exact cmath interception, and link requirements;
- `intrinsics/libdevice-math.md`: the mapping reference.

The importer, MIR lowerer, and rustc collector consume the shared generated
dispatch instead of maintaining their own copies. Type-aware generic core
intrinsics and the semantic expansions for frexp, modf, remquo, lgamma_r,
sincos, legacy min/max, C23 min/max, j1 infinity correction, and fast
arithmetic remain handwritten. For example, before and after regeneration,
`libm::math::scalbn::scalbnf` resolves to `LdexpF32`, emits the same ldexp
placeholder, and lowers to `__nv_ldexpf` with an i32 exponent.

`generate` owns and reconciles both outputs; `check` rejects drift in either
of them, including the compiler dispatch. A regression fixture records the 214
scalar compiler paths before migration and compares them against the compiled
consumer's identities, placeholders, symbols, and link classification. Separate
controls cover sincos, generic fabs, native LLVM routes, and unknown names.

This input is read separately from the hardware shard index in
`intrinsics/overlay.toml`. Its evidence comes from `libdevice.10.bc`, so it does
not receive hardware ABI IDs or change the hardware catalog hash. Ordinary
unindexed hardware shards remain errors.

Rows name a Rust signature class, optional libm aliases, core intrinsic names,
compatibility paths, cmath spelling, placeholder suffixes, libdevice symbol,
native LLVM alternative, link classification, and handwritten handler. By
default, a row exports its name from libm; `libm = []` explicitly describes a
core-only operation. `{width}` expands to `f32`/`f64`, `{Width}` and `{WIDTH}` to
`F32`/`F64`, and `{suffix}` to `f`/the empty string. Variant and constant overrides
preserve existing compiler identities such as `PowfF32` and the generic `Fabs`.

Unknown fields, duplicate paths/identities/placeholders, invalid templates,
ambiguous C ABIs, incompatible link classifications, and unsupported handwritten
handlers fail before outputs are written. Tuple signatures require a supported
handwritten adapter.

Generation checks all 102 verified libdevice signatures against the pinned
capture in `intrinsics/evidence/libdevice_math/cuda-13.0.json`. Its provenance
and reproduction instructions are recorded beside it. Ordinary `generate` and
`check` do not need a CUDA installation.

To verify the same ABI against a locally installed toolkit:

```bash
libdevice_llvm_dis="$(rustc --print sysroot)/lib/rustlib/$(rustc -vV | sed -n 's/^host: //p')/bin/llvm-dis"
cargo run -p cuda-intrinsics-gen --locked -- verify-libdevice \
  --libdevice "${CUDA_PATH:-/usr/local/cuda}/nvvm/libdevice/libdevice.10.bc" \
  --llvm-dis "$libdevice_llvm_dis"
```

Verification accepts compatible newer toolkit bitcode and reports its hash.
To refresh evidence, review and update the shard's bitcode hash pin, then run
`extract-libdevice` with the same arguments, followed by `generate` and `check`.
Extraction hashes and disassembles the same bytes, requires exported definitions
with exact return/argument types, and writes only after all referenced signatures
pass. Opaque pointers do not encode their pointee type; out-parameter semantics
remain the handwritten adapter's responsibility.

Validation from `cuda-oxide/`:

```bash
cargo test -p cuda-intrinsics-gen -p dialect-mir -p mir-importer -p mir-lower --locked --all-targets
cargo clippy -p cuda-intrinsics-gen -p dialect-mir -p mir-importer -p mir-lower --locked --all-targets -- -D warnings
cargo run -p cuda-intrinsics-gen --locked -- check
cargo test --manifest-path crates/rustc-codegen-cuda/Cargo.toml --locked --lib
just check
```
